# Release 4 forward-only payout boundary

## Policy and current result

The six completed online trips paid externally under the old arrangement remain historical. They are not payout backfill candidates, are not marked bank verified, and are excluded from Release 4 payout totals. A Yoco fee export for those six is not required for this forward-only policy. Existing trip and ledger rows remain untouched.

The payout model begins only for trips whose authoritative `trips.completed_at` is at or after the owner-approved `MOOVU_PAYOUT_EFFECTIVE_AT` UTC instant. The cutoff is recorded once in `online_payout_policy` with an approval reference and approving Auth user, and cannot be changed after recording. The application sends its configured cutoff to the database on each payable posting; a mismatch or missing activation fails closed and keeps the durable recovery job retryable. The old direct posting RPC is revoked from `service_role`. A database trigger rejects a payable or payout item for a pre-cutoff trip. Missing or unverified actual Yoco processing fees remain pending, never estimated as a confirmed net payout.

Fare activation has a separate `MOOVU_FARE_EFFECTIVE_AT` UTC instant. Both the fare flag and a reached valid timestamp are required. It applies in the authoritative quote and booking path to new customer-visible quotes; stale quotes are rejected by version/amount checks. Existing locked trip fares are unchanged.

## Evidence and limits

- Exact approved baseline: `2165be51452c1a8f4f8c05b57cd7509eabcc950f`. The new branch is isolated from the existing dirty Stage 2 checkout.
- The current schema-only archive was restored into a local PostgreSQL 17 container. All five existing migrations, unchanged, then the new sixth migration applied. A separate hash-pinned sixth runner applied it again from a reconstructed pre-sixth fixture and recorded one migration-history row. A second run refused the already-applied history. Synthetic assertions verified historical exclusion, mismatched-cutoff rejection, immutable activation, backdate rejection and service-role RPC grants. The fixture transaction rolled back; no production connection was made.
- The original fifth SQL file remains unchanged. Its approved hash is for CRLF bytes while Git checks it out as LF. The five-file runner now reconstructs the reviewed CRLF bytes before SHA-256 validation and execution; arbitrary content still fails the hash check.
- Authenticated hosted Admin and Driver payout acceptance, current managed-role equivalence for the sixth migration, real post-cutoff Yoco fee evidence, and bank-statement verification have **not** been performed. Manual payment recording and bank verification remain disabled. The UI labels unbatched earnings as preliminary and shows pending fee verification. Neither an empty new-model list nor the historical six is reported as zero Driver entitlement.
- Certified database and Storage backups are historical recovery points; they do not recover later writes by themselves. Production release requires a current write-preserving cutover check. Do not use database restore as an application rollback.

**Decision:** Technical local forward-only guard passes. Production SQL, hosted acceptance, deployment, payout activation and fare activation require separate owner approvals and live verification. Release 4 is not live.
