# Phase 3 SHADOW accounting and Yoco contract readiness review

Date: 2026-09-12. **Verdict: BLOCKED for production finance coexistence.** This is a read-only review. No SQL was written, no Yoco API was called, and no deployment, webhook registration, configuration change, or activation occurred.

## Production Phase 2 and exact online interaction

Read-only production project `mvazbszenqahgqpznhhq` reports `phase2_finance_policy.mode=SHADOW`, `effective_from=2026-09-11 18:04:00+00`, and `go_basis_points=1500`. AUTHORITATIVE is off by that database policy. Phase 3 attempts table, trusted processor and payable RPC are absent. One existing `trip_commission:*` Phase 2 transaction is POSTED, with two entries: 1,080 cents debit to `DRIVER_COMMISSION_DEBT` and 1,080 cents credit to `COMMISSION_REVENUE`; one reconciliation row exists. These are aggregate read-only counts, not a Phase 3 transaction. The current encrypted application environment mode was not independently read; source behavior below is conditional on `MOOVU_PHASE2_FINANCE_MODE=SHADOW` at runtime.

`src/lib/finance/phase2Policy.ts` resolves only literal SHADOW/AUTHORITATIVE, otherwise OFF. `completeTripServer.ts` calls the legacy `phase05b_complete_trip` first, then `postShadowTripCommission` in SHADOW, then the Phase 3 online payable RPC for online trips. The legacy completion remains financially authoritative and sets the current commission and Driver net. The SHADOW RPC `phase2_post_trip_commission` in `docs/phase-2-commission-driver-finance-migration.sql` posts a real `TRIP_FINANCIAL_COMPLETION` / `TRIP` Phase 1 transaction using `phase1_post_financial_transaction`: debit `DRIVER_COMMISSION_DEBT` and credit `COMMISSION_REVENUE` at the future locked 15%. It also writes `phase2_shadow_reconciliations`. Its source key `trip_commission:<trip>` and metadata distinguish it if queries deliberately filter, but the account balances and default POSTED transaction class do not segregate it from authoritative money.

The proposed `docs/phase-3-online-completion-payable.sql` then posts `online_service_completion:<trip>` as a POSTED `ADJUSTMENT`: debit `UNAPPLIED_FUNDS` R100, credit `DRIVER_EARNINGS_PAYABLE` R90, credit the **same** platform `COMMISSION_REVENUE` account category R10, and links one online payable. The trusted-payment processor previously debits processor/payment clearing R100 and credits customer funds liability R100. Provider fees and actual settlement remain unknown and clearing stays open. With both application paths active in production SHADOW, this hypothetical R100 trip would therefore leave a R90 payable **plus** an observational R15 Driver commission debt, and R10 + R15 = **R25 of POSTED commission revenue credits**. Customer liability moves only once; no second R100 liability release is evident. The Phase 2 R15 debt is not the Driver payout, but financial summaries or balances that treat all POSTED account entries as authoritative would be contaminated. `phase2_driver_finance_position` does sum this POSTED debt; `phase2_finance_eligibility` still selects legacy debt/subscription for authoritative eligibility while mode is SHADOW, so dispatch authority is not shown to change, but displayed Phase 2 position can be mistaken for collectible debt. This is a genuine blocker before deploying the Phase 3 completion path with SHADOW.

Narrow proposed correction for a later, separately authorized gate: keep Phase 2 SHADOW observations in `phase2_shadow_reconciliations` or another explicitly non-authoritative observation store, while preventing new SHADOW-mode posts to authoritative Phase 1 accounts. Do not alter legacy completion, current R10/R90 economics, the Phase 3 liability release, or existing historical SHADOW entries in this review. Define an explicit treatment of existing SHADOW ledger rows for financial read models and reconciliation; validate R100 online plus Cash and Transfer against a disposable SHADOW policy and replay/concurrency before production review. Do not simply skip SHADOW observation or delete its history.

## Transfer regression

The customer booking UI labels the value `cash` as “Cash / Transfer”; `src/app/api/customer/book-trip/route.ts` accepts only `cash` or disabled `online` for customer bookings. Thus the connected Cash trip exercises the same stored payment method used for customer-facing Transfer. Admin-created trips can use `other`, which is a distinct legacy value, and should be checked separately if it is used operationally as Transfer. A separate disposable Transfer UI-to-booking assertion is preferable; a distinct financial E2E is low risk for customer bookings because the stored method is `cash`.

## Architecture fit, security, and next gate

The existing `src/lib/payments` provider interface maps Yoco checkout `id` to provider checkout reference, `paymentId` when present to payment reference, hosted `redirectUrl` to customer navigation, and a verified event to the durable provider inbox/attempt transition. The internal attempt, `verified_at`, reconciliation/refund records, pre-service ledger, completion reclassification, payable and receipt/read models are suitable boundaries. `FAKE_TEST` is internal test-only and `MOOVU_ONLINE_PAYMENTS_ENABLED` remains fail-closed; normal booking does not expose provider selection. The server must retain the secret key, validate locked amount/ZAR and provider references, avoid card PAN/CVV storage, minimize/redact raw payloads/logs, and never let return URL or client input set success. The provider adapter and signed ingress do not yet exist. Checkout idempotency expires after 24 hours, so MOOVU's own durable idempotency remains necessary. [Yoco idempotency](https://developer.yoco.com/docs/checkout-api/idempotency)

**Smallest real-Yoco implementation gate:** local/disposable **sandbox Checkout creation only**: server-side test-key adapter, locked amount/ZAR, idempotency key, checkout ID/redirect URL storage, safe customer redirect and pending state. No trusted success, dispatch unlock, refund, payout, webhook registration, production mutation or Pay Online activation. Separately, before production deployment, correct SHADOW posting isolation and test online/Cash/Transfer under disposable SHADOW; then implement signed Checkout ingress using the newly clear official algorithm and verify against an actual official test delivery. Confirm merchant eligibility and status retrieval/settlement access with Yoco. No part of this review authorizes those actions.
