The read-only `scripts/yoco-unresolved-review.mjs --inventory` lists production Customer and Driver attempts in CREATED/PENDING states, without settlement. With existing owner-controlled LIVE credentials in a private process environment, `--verify` additionally queries the bound Checkout ID and checks checkout ID, amount, currency, mode, attempt metadata and trip/Driver binding. It classifies provider-completed local attempts for operator investigation; it does **not** call a settlement RPC, modify records or synthesize a webhook. A provider lookup failure remains uncertain.

The operator must compare each flagged attempt with the provider's authoritative record and the application's existing provider-event and reconciliation records. If a signed provider retry arrives, let the existing idempotent webhook path process it. Otherwise use only an existing, separately authorized trusted reconciliation procedure after verifying the provider evidence and exact binding; do not change a row to PAID manually. Re-run inventory and financial invariant checks afterward. Duplicate signed-event and replay behavior is covered by the existing focused payment tests. Provider retry timing and end-to-end HTTP delivery cannot be guaranteed from this local rehearsal alone. Keep a monitored unresolved-attempt list until provider acceptance is observed or the provider confirms a terminal non-success state.

During the cutover, the release operator owns this monitoring: capture an inventory immediately before staging, after migration, after promotion, and after the observation window; compare newly created attempts, verified/processed provider-event counts, and application webhook errors. Escalate immediately if a newly CREATED/PENDING attempt remains unresolved after the normal checkout return, a provider event is VERIFIED but not PROCESSED, webhook responses fail, provider status cannot be retrieved, or a completed LIVE checkout lacks a matched MOOVU attempt. Keep the webhook route available and investigate provider retry status and the bound checkout using the private, read-only `--verify` mode. Existing historical PENDING records remain individually uncertain until verified; age alone never authorizes settlement or deletion. No automatic monitor or guaranteed Yoco retry interval is established by this runbook.
