# MOOVU deletion / foreign-key audit

## Status
Read-only production schema inspection plus local code inspection. No deletion implementation, FK migration, data mutation or deployment performed. This is a first-pass full public-schema FK inventory, not approval of any cascade or hard-delete operation. Semantic retention and orphan/snapshot validation remain incomplete.

## Verified findings
- Production public schema has 117 FK constraints; every one is listed below.
- driver_wallets.driver_id is UNIQUE, NOT NULL and ON DELETE RESTRICT. Its fields include balance_due, total_commission, total_driver_net and payment summaries. This is a financial projection, not disposable profile metadata.
- driver_wallet_transactions references both drivers and wallets with RESTRICT. Deleting the wallet or Driver is deliberately blocked when those references exist.
- trips has RESTRICT dependencies including financial_transactions.economic_trip_id, trip_events, Phase 4 fee assessments/grace/quotes and Phase 5 credit/referral records. Manual deletion failures are therefore expected integrity protections.
- Existing driver_payment_requests, driver_subscription_charges/events/requests/subscriptions still cascade from drivers. Do not broaden direct deletion; confirm and protect their financial/audit significance first.
- SET NULL on wallet transaction trip references does not by itself prove a financially significant trip is safe to delete.
- Financial accounts and transaction metadata may use polymorphic owner IDs or JSON references without FKs. FK absence is not evidence of no economic history.

## Current code and risk
- src/app/api/admin/drivers/remove/route.ts implements deactivate/anonymize while retaining the drivers row. Its permanent label does NOT physically remove the Driver identity.
- The route unlinks driver_accounts before the later Driver update and uses multiple non-transactional requests. A later failure can leave the account partially removed. Errors from some follow-up profile/notification operations are ignored.
- src/lib/account-deletion/service.ts performs multi-step cleanup/anonymization and then Auth soft deletion. Some failures are logged but do not block success. This requires a durable resumable workflow, not a broad FK cascade.
- src/lib/dispatch/dispatchCandidates.ts filters is_deleted and rejects deleted candidates. Preserve this and all other eligibility paths if archival is extended.
- docs/phase-05d-004-retention-security.sql already describes RESTRICT protections; several are verified installed. Do not reverse them merely to make Table Editor deletion convenient.

## Dependency graph
Drivers -> wallets -> wallet transactions / settlements; Drivers -> trips / financial-policy records / subscription payment records.
Trips -> financial transactions / commission recovery / cancellation assessments / credit redemptions / referral qualifications / trip events.
Customers -> cancellation liabilities / membership payments / memberships / credits / referral relationships.
These identities should normally remain as inactive/anonymized tombstones while economic references survive.

## Recommended architecture (review only)
1. Keep RESTRICT/NO ACTION for financial and audit dependencies.
2. Reuse existing parent deactivation/anonymization fields rather than inventing parallel deletion columns.
3. Add a separately approved Admin-only transactional deletion/preflight RPC for truly disposable records. Lock the parent, check active work and all direct/indirect/polymorphic economic references, then delete only proven disposable children in deterministic order. Keep an external durable audit event surviving deletion.
4. Use a durable workflow for Auth and Storage cleanup, which cannot share a PostgreSQL transaction. Persist progress, retry safely and never report completed cleanup when required steps failed.
5. For financial/history-bearing entities return an archive-required refusal. Do not erase ledger ownership or reconcile debt by deleting records.
6. Direct Table Editor DELETE should remain intentionally blocked for protected entities. A completed/paid trip is not test data merely because an owner wants to remove it.

## Proposed migrations (not created / not applied)
- Narrow protection migration only after inspecting the data and authority of legacy cascading payment/subscription relationships. Preserve constraint names, indexes, RLS and rows; orphan and snapshot checks required first.
- Controlled deletion/archival RPC with explicit Admin grants, transaction locks, financial retention rules and durable audit.
- Durable cleanup workflow only if existing account deletion infrastructure cannot safely resume required operations.
No migration is approved by this report.

## Expected application surfaces
Admin Driver removal, Customer/Driver account deletion, any Admin trip archival UI, dispatch eligibility, history/reporting filters and cleanup jobs. Preserve receipt/report access for retained historical records.

## Validation still required before implementation
Inspect all table semantics, soft-delete fields, indirect/polymorphic links, trigger behavior, current grants/RLS, actual snapshot coverage and orphan counts. Run approved disposable tests for unused versus financial Drivers/trips, active-work races, cleanup failure/retry, unauthorized calls and ledger preservation. No connected deletion test was run.
