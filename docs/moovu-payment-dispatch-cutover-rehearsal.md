## Required cutover boundary and cron drain

A safe cutover is **not yet demonstrated**. The minimum compatible cutover package must make the unchanged code unable to create a new paid offer *before* the corrected coordinator is allowed to work. It must cover both the cron route and signed webhook path, including invocations already in flight. A reviewed database-backed pause/fence is the smallest plausible shared boundary: reject claimless initial paid-offer reservations while paused, preserve `SUCCEEDED` payment attempts as retryable without burning the ten-attempt budget, and leave signed webhook verification/financial commit available. That pause/fence is **not implemented or tested in this candidate** and needs separate SQL review and disposable old-code/webhook rehearsal. A frontend flag or disabling cron alone is insufficient.

Operationally, stop new scheduled invocations, activate the reviewed shared fence, then wait at least the deployed function execution limit plus queue/request slack and verify no claimless invocation remains. Reconcile any offers created before the fence and all `SUCCEEDED` attempts that remain `PENDING` or `FAILED`. Signed webhooks must continue to commit verified payment evidence and report dispatch pending, not falsely report a new offer as complete. Only after the fence and drain are proven may the corrected code be introduced; release the pause only when the corrected worker is the sole execution path. Monitor pending attempts, claim leases, expiry jobs, offer rounds and notification attempts. The exact timing and fence behavior remain unverified.

## Recovery and limits

For a failed corrected dispatch, wait for the bounded lease to expire, inspect the `SUCCEEDED` attempt and its round/offers, then let the corrected cron recovery reconcile the existing offer and queue its expiry job. Do not replay a payment settlement or insert an offer directly. For duplicate invocations, the database claim should return `BUSY` or `DONE`; investigate any different outcome. For an interrupted worker, never infer push delivery from an offer row. For rollback, switch only to a corrected compatibility artifact; keep the database and later financial records intact.

This run did not prove full payment-processor idempotency, provider delivery, zero duplicate financial posting under the real trusted SQL processor, managed Supabase behavior, or a production cron drain. The first mandatory failure already prevents release certification. No live webhook or cron was invoked, no production SQL/configuration/deployment was changed, and neither Release 4 financial flag was enabled.
