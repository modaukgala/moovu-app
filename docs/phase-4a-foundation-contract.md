# Phase 4A local foundation contract — review only

This is a local design and schema package, not a release or an effective policy. No application route, production RPC, booking eligibility, posting helper, or environment setting invokes it. `phase-4a-financial-state-foundation.sql` is **not applied**. The SQL inserts no policy row and does not backfill or update historical cancellation rows. Its seven new tables are empty on installation. Production cutover and any effective date require separate review.

## Owner policy and authoritative decision

`src/lib/finance/phase4Policy.ts` contains the approved version `phase4-2026-09-owner-v1`, ZAR integer cents, 180-second free window and 300-second no-show wait. Its sentinel `effectiveFrom=9999-12-31T00:00:00Z` prevents accidental selection before an approved cutover. A later approved policy row must use an explicit effective timestamp; immutable versions allow later policy changes without reinterpreting history. `elapsed < 180 seconds` is free and `elapsed >= 180 seconds` is potentially chargeable. The future database decision must use its clock and locked trip state. Unassigned/requested/offered trips remain free regardless of time. Customer cancellation after arrival remains late cancellation. No-show needs authenticated assigned Driver, qualified server-recorded arrival, eligible arrived state, and `elapsed >= 300 seconds`. No client fee or countdown is authoritative.

The current production RPC still uses the old time-only unassigned rule and the existing client has an inclusive 180-second boundary. Those are explicitly reserved for a later, separately approved 4B/4C cutover. Do not present the Phase 4A helper as active production policy.

## Source and state contracts

`phase4_fee_assessments` stores a one-per-trip immutable snapshot of trip, Customer, Driver, fee type, service, policy version/effective time, server assessment time, clock basis, locked state/assignment, exact cents, arrival evidence version when applicable, source key, and idempotency key. Its original row remains `ASSESSED`; a later reversal is represented by a linked, append-only financial action and compensating Phase 1 transaction, not by editing the original. The current `trip_cancellation_fees` rows remain untouched.

`phase4_customer_liabilities` tracks the original amount as the sum of open, collected, waived, reversed and written-off cents. `ASSESSED` is not yet a finalized debt. `OPEN` is finalized, undisputed and unpaid; `DISPUTED` does not qualify for booking restriction. `RESOLVED`, `WAIVED`, `REVERSED`, and `WRITTEN_OFF` require an actor, reason, timestamp and zero open amount. A database trigger protects the original amount, assessment/Customer/source identity and creation time while allowing controlled state/amount-allocation updates. State transitions and allocation changes must occur inside the future privileged 4B transaction with action records and ledger effects; Phase 4A does not expose a mutation API. A waiver of a partially collected fee requires a refund/adjustment decision; it cannot simply move already collected cents to `waived_cents` without a corresponding financial action.

`phase4_driver_compensations` is one per assessment. The Driver earns the specified cents at valid assessment, independently of Customer collection. `EARNED` does not mean cash paid. `PAYABLE`, `CREDITED`, `SETTLED`, and `REVERSED` are separate projections. The database protects original earned cents and source identity against update. A future settlement or legacy commission offset needs an independently verified, source-linked event. No second Driver wallet is introduced, and compensation never enters Phase 2 completed-trip fare commission.

`phase4_financial_actions` gives append-only, unique source keys to collection, dispute, waiver, reversal, write-off and compensation settlement. Stable keys use `phase4:<action>:<source-id>`. Retry with the same key must verify the stored payload and return the existing outcome; a different payload with the same key must fail. A future privileged writer must validate the requested transition, exact amount, actor role, source link, and ledger outcome in one transaction. Database uniqueness is the final duplicate guard.

## Two-completed-rides grace

The first finalized, undisputed, unpaid qualifying liability opens one Customer grace cycle. Another fee while that cycle is active joins it; it never restarts two rides. A future trip-completion handler records a unique consumption only if a completed trip occurs while qualifying debt is open and undisputed. Booking attempts, declines, expiries, cancellations and no-shows record none. At zero, one and two consumptions, the remaining allowance is two, one and zero. The *next* booking is restricted at two. Active disputed debt is excluded; if it is the only debt, the restriction is off and completed rides while disputed consume none. Prior valid consumptions remain auditable and are restored if a dispute is resolved against the Customer. Once every qualifying debt is paid/waived/reversed/otherwise formally resolved, close the cycle. A later new finalized debt starts a new cycle. No booking route reads this model in Phase 4A.

The pure evaluator consumes stored qualifying completion records; the eventual 4C completion writer must verify completion using the authoritative server transition and write the consumption atomically with that transition or via a unique durable event. This avoids retrospectively counting an unrelated trip, especially across disputed periods. The one-active-cycle index prevents parallel grace resets.

## Phase 1 posting boundary

Existing Phase 1 transaction categories include `CANCELLATION_FEE`, `NO_SHOW_FEE`, `DRIVER_CANCELLATION_COMPENSATION`, `CUSTOMER_PAYMENT`, `REVERSAL`, and `REFUND`. Existing account categories include `CANCELLATION_NO_SHOW_RECEIVABLE`, `DRIVER_COMPENSATION_PAYABLE`, `CANCELLATION_NO_SHOW_REVENUE`, `ADJUSTMENT_CLEARING`, `PAYMENT_CLEARING`, and `UNAPPLIED_FUNDS`. No new category is needed in 4A.

Proposed assessed-but-uncollected Go cancellation: debit Customer receivable 2,000 cents, credit Driver compensation payable 1,300, credit assessment/economic clearing 700. Go no-show: debit receivable 3,000, credit payable 2,200, credit clearing 800. These are balanced and assert **no cash received**. Later verified collection debits payment clearing and credits receivable. The exact reclassification of MOOVU's clearing portion into revenue, and its timing, require professional accounting approval; until then the proposed journal does not credit revenue. Driver payout/legacy offset is a separate settlement action debiting payable against an actual settlement/offset account. Waiver, reversal, write-off and refunds need source-linked compensating entries, never deletion. The pure `assessedFeeJournal` is only a draft contract; `PHASE1_LEDGER_WRITE_ENABLED` remains false.

The existing Phase 1 source validator recognizes `TRIP_CANCELLATION_FEE` against legacy `trip_cancellation_fees`. 4B must decide whether the terminal Phase 1 transaction links to that existing fee row plus the new snapshot or minimally extends the validator for `phase4_fee_assessments`; neither source contract is changed in 4A. The Phase 1 one-terminal-transaction-per-trip constraint and the new one-assessment-per-trip constraint must be reconciled in disposable before any posting activation.

## Migration, recovery, and historic isolation

The SQL is additive: new policy, assessment, liability, compensation, grace-cycle, grace-consumption and action tables; indexes, constraints, RLS, service-role SELECT grants and append-only triggers. No policies permit client writes. Future writes require separately reviewed security-definer RPCs. The package contains no insert into existing tables, no existing function replacement, and no loop or backfill over the 26 historical fee rows. Thus it creates no historical debt, Driver payable, cancellation credit, or Phase 1 entry. It is still subject to disposable schema/FK/grant validation before production review. Transaction failure rolls back installation. A later rollback of populated objects needs a reviewed data/reconciliation plan; automatic `DROP` is inappropriate.

Phase 2 mode, effective date, subscriptions, 15% observation and R50 observation are untouched. Phase 3 online payments and refunds are untouched. Phase 4B atomic posting, 4C routes/UI, dispute implementation, production migration and activation remain separate gates.
