# Admin finance unification: release gates

This branch does not change financial posting, provider verification, dispatch, or production data.

## Commission authority

- Driver Earnings, Driver Commission Payments, and the new paged Admin commission list use `resolveDriverFinanceAuthority`. In `AUTHORITATIVE` mode, `phase2_finance_eligibility.net_owed_cents` is the outstanding amount. In `OFF`/`SHADOW`, the legacy wallet balance is used. Missing legacy wallets are shown as unavailable, not zero.
- The Admin aggregate is intentionally unavailable. The current schema exposes a per-Driver authority RPC, not a verified, point-in-time aggregate across every Driver. Summing a paged subset or wallet snapshots would be misleading.
- The Admin wallet breakdown GET no longer calls the wallet-refresh write RPC. Historical transaction rows are a recent sample, not the source of the current balance.
- Same-Driver authenticated parity remains unverified until existing authorized Customer/Driver/Admin sessions and an agreed ledger snapshot can be used. The Driver earnings GET still refreshes the legacy wallet, so read-only comparison must avoid invoking that route until its behavior is separately reviewed.

## Commission posting verification (no posting change)

- The installed `phase05b_complete_trip` definition uses the Phase 2 authoritative cutoff and skips the legacy `driver_wallet_transactions` debit and wallet refresh for post-cutoff trips. It retains 10% Go, 12% XL, and 9.5% fallback only for legacy-mode trips. The older `docs/phase-5-atomic-operations.sql` is not the installed authoritative-cutover definition.
- Production policy is AUTHORITATIVE with 1,500 basis points for Go and XL and a 2026-09-15 19:04:38 UTC cutoff. The completion function records 15% trip commission for post-cutoff trips. `phase2_post_trip_commission` charges the locked `commission_basis_points` snapshot exactly once under `trip_commission:<trip UUID>`; for Phase 5 trips it uses `phase5_driver_fare_basis_cents`, matching completion. The ledger is the financial authority; trip commission fields are the matching presentation/audit projection, not a second debit.
- Read-only production aggregates on 2026-10-14 found 55 completed post-cutoff trips: zero non-15% snapshots, zero trip commission amount mismatches, and zero legacy commission debit rows. All 55 post-cutoff trip reconciliation rows have parity. Four non-parity trip reconciliation rows belong to pre-cutoff trips and must not be silently repriced. All 56 durable recovery jobs currently show `succeeded`; this is a point-in-time check, not a proof that future jobs cannot fail.
- Current supported production ride options over the preceding 90 days were `go` and `group`. The snapshot trigger maps an unrecognized option to the Go rate; it does not apply the legacy 9.5% fallback to post-cutoff work. A stricter ride-option rejection policy would be a separate business-rule and migration review, not a prerequisite to correct the alleged double posting.
- Completion and ledger posting are separate transactions. A temporary posting failure leaves a durable recovery job and temporarily understates authoritative Driver Commission Due until the idempotent job succeeds. Terminal jobs, worker scheduling, and alerting remain operational release checks. No historical rows, balances, or payment records were changed for this verification.

## Payment review migration

`supabase/migrations/20261013120000_admin_yoco_payment_review.sql` was applied to the disposable project `tangtlmdpnvmoviwrgvd` only. The forward-only `20261013120100_admin_yoco_review_checkout_search.sql` was also applied there after a checkout-only reference failed to match. Both migrations must be reviewed and approved separately for production before this branch is deployed. The API fails with 503 while the RPC is absent; it does not fall back to the old, incorrectly paginated review.

The RPC filters before pagination, returns exact matching counts, and uses the existing verified, processed Yoco success event to label a payment as verified paid. Refund-related attempt states are flagged for investigation, not described as confirmed refunds: an authoritative provider-and-ledger refund path was not established. It does not call Yoco or write finance data. Roll back by dropping only `public.admin_yoco_payment_review(timestamptz,timestamptz,text,text,text,integer,integer)`.

Disposable checks with 20 Yoco attempts confirmed exact/partial payment and checkout reference search, no-match search, inclusive lower and exclusive upper timestamps, same-day search, filtered pagination and counts, and unauthorized-role rejection. No existing record has a duplicate sort timestamp, no-trip verified payment, accepted Driver allocation, or refund state. Read-only `VALUES` fixtures exercised the corresponding CASE expressions but did not execute the function on persisted examples. Local tests remain source-contract checks, not PostgreSQL execution proof for those missing cases.

A read-only representative `EXPLAIN ANALYZE` took about 1 ms on 20 attempts. It used a sequential scan of `online_payment_attempts`, materialized the full date slice, performed per-attempt event lookups, then sorted and paged. This is appropriate for the tiny disposable dataset but does not prove production-scale performance. There is no `(provider, created_at)` index; consider a separate, reviewable index migration only after production-safe cardinality and query-plan review. Exact totals necessarily scan the filtered slice, so an index alone will not make arbitrary 366-day counts constant-time. No performance index was applied to either database. Authenticated Admin/Driver finance parity and real payment lifecycle checks remain separate release gates.
